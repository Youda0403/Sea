# SF 아포칼립스 자캐 탐사 텍스트 게임 — 제작 계획서 v1.0

> **문서 목적:** 사람 개발자와 다른 AI가 같은 규칙을 이해하고, 기능을 분담하여도 데이터·서사·UI가 충돌하지 않게 하는 기준 문서. 이 문서는 *실행 가능한 설계안*이며 실제 구현·검증을 마친 결과 보고서가 아니다.  
> **현재 결정:** 모바일 웹 우선 / 싱글 플레이 / 플레이어가 직접 선택 / 주인공은 자캐 안드로이드 / 규칙 기반·AI API 미사용 / SF 아포칼립스 탐사 / 선택을 거부할 수 있는 캐릭터 / 기억·일기·아이템 / 기존 《창해의 프시케》는 일부 설정과 정서만 참고하는 독립 작품.  
> **미확정:** 게임의 정식 제목, 미스터리의 진상·정사, 최종 아트 스타일, 공개판 분량. 이 문서의 수치·명칭·줄거리는 달리 표시하지 않는 한 **개발용 제안값**이다.

---

## 0. 한 장 요약

**게임의 한 문장:** 인류가 사라지고 바다에 잠긴 미래에서, 플레이어가 직접 만든 안드로이드로 폐허를 탐사하고 선택한다. 주인공은 고유한 성격·가치관·경험 때문에 어떤 선택을 주저하거나 거부할 수 있으며, 모든 실제 행동은 기억과 일기에 남아 다음 선택에 영향을 준다.

**핵심 약속:** (1) 플레이어가 이야기의 진행을 주도한다. (2) 주인공은 플레이어의 존재를 알지 못하며 제4의 벽을 넘지 않는다. (3) 선택 거부는 희귀하고 이유를 이해할 수 있어야 한다. (4) 강제 개입 아이템은 거부를 무시할 수 있지만 물리적 성공이나 NPC 반응까지 보장하지 않는다. (5) 사건의 사실, 캐릭터의 해석, 화면에 보여줄 문장을 분리한다. (6) AI가 없어도 오프라인에 가까운 정적 웹앱으로 핵심 플레이가 작동한다.

**제품 형태:** 세로형 모바일 화면에 최적화된 HTML/CSS/TypeScript 정적 웹앱. PC 브라우저도 지원. 저장은 IndexedDB, JSON 백업/복원 지원. 온라인 로그인·멀티플레이·실시간 3D·생성형 스토리·서버 동기화는 초기 범위 밖.

**개발 원칙:** 분량보다 반응의 의미를 우선한다. 이벤트 100개를 무관한 문장으로 채우는 대신, 12개라도 서로 다른 성격·기억·장비에 의해 유의미하게 변화하도록 만든다.

## 1. 기획 목표와 비목표

### 1.1 플레이어가 느껴야 할 재미

- **내가 만든 캐릭터다:** 이름·프로필·이미지·기체 목적·성격·가치관·기억의 출발점을 설정한다. 사용자가 쓴 자유 텍스트는 소개·표시용이며, 구조화된 설정만 규칙에 반영한다.
- **내가 직접 조작한다:** 지역 선택·조사·대화·도구 사용·행동 선택은 플레이어가 결정한다. 캐릭터가 혼자 하루를 보내는 관찰형 게임이 아니다.
- **그런데 나만의 의지도 있다:** 주인공이 중요한 성격 충돌에서 주저·대안 제시·거부할 수 있다. 빈번한 랜덤 방해는 금지.
- **행동에는 흔적이 남는다:** 특정 인물을 도왔다면 해당 인물이 재등장하고, 버렸다면 후속 사건이 달라질 수 있다. 단순한 문장만 바뀌는 가짜 분기를 최소화한다.
- **캐릭터가 자기 삶을 회고한다:** 기억은 객관적 기록, 일기는 주관적이되 실제 사실에 모순되지 않는 회고. 일기는 숨겨진 성격 변화의 힌트다.
- **폐허를 탐험할 이유가 있다:** 장비·부품·단서·새 지역·짧은 메인 미스터리·서브 사건·제작이 연결된다.

### 1.2 피해야 할 경험

- 실제 선택이 무시되었는데 이유 설명 없이 같은 결과로 합류하는 것.
- 성격 수치가 전부 공개되어 최적 행동을 계산하는 스탯 퍼즐이 되는 것.
- 아이템이 모든 사건을 무조건 해결하는 만능키가 되는 것.
- 일기가 발생하지 않은 사건을 사실처럼 쓰거나 나중에 다시 열 때 내용이 바뀌는 것.
- 사건 출현 RNG 때문에 메인 스토리가 무기한 막히는 것.
- 캐릭터 유형마다 사실상 별도 게임을 만들어야 하는 콘텐츠 폭발.

### 1.3 플레이 타깃

자캐/오리지널 캐릭터에 애착이 있고, 텍스트 어드벤처·선택지·육성·탐사·수집을 좋아하는 플레이어. 모바일에서 짧게 이어 플레이할 수 있어야 하며, 긴 장면은 읽기 쉬운 단락과 기록 기능으로 보완한다.

## 2. 세계관 바이블 — 확정과 제안의 경계

### 2.1 기존 작품에서 참고할 모티프

- 인류가 떠나거나 사라진 뒤 바닷물에 잠긴 미래의 도시와 남겨진 기계 문명.
- 인간형 안드로이드의 **코어(핵심 동작 부품)**, 배터리, 부식, 부품 교체, 폐기된 기체.
- 제작 목적·오래된 명령·스스로 생겨난 가치관 사이의 충돌.
- 바다의 아름다움과 기계 잔해의 쓸쓸함, 그리고 폐허 속에서도 이어지는 작은 공동체.

**독립 작품 원칙:** 《창해의 프시케》의 PC/KPC, 살라미·마리네이드·뽀삐, 아니마·소마, 12개체만의 사명 폭주, 기존 시나리오의 사건·반전·엔딩은 이번 게임의 필수 정사로 사용하지 않는다. 원작의 코어 설정과 분위기를 참고하되 새 세력·장소·사건을 만든다. CoC 시스템과 크툴루 신화의 고유 설정도 게임에 그대로 이식하지 않는다. 니어 오토마타는 정서적 참고일 뿐 고유 아트·음악·캐릭터·용어를 복제하지 않는다.

### 2.2 새 게임의 배경 초안

가제: **《잔해의 항로》**(가제이며 미확정). 인류가 사라진 뒤 수십 년은 아닌, 기계 문명과 인간의 유산이 동시에 남아 있을 만한 시기를 배경으로 한다. 해수면 상승으로 육지의 대부분이 상실되고, 남은 고지대·돔·해상 플랫폼·제방 도시에 안드로이드와 기타 로봇 공동체가 흩어져 살고 있다. 오래된 인간 네트워크와 자동화 공장은 일부 작동하지만 안정적이지 않다. 바닷물·전력 부족·부품 규격 불일치는 직접적인 생존 제약이다.

### 2.3 중심 미스터리 초안 — 확정 아님

폐기된 연안 중계 시설에서 오래된 **동기화 신호**가 간헐적으로 송출된다. 일부 호환 기체가 오래된 임무를 떠올리거나 특정 지역을 향해 이동한다. 주인공은 이 신호를 조사하면서 사라진 기술 문명의 기록과 현존 공동체의 이해관계에 접근한다. 신호는 **일반적인 행동 개입 기술**과 연결될 수 있으나, 인류가 멸망한 원인이나 모든 기체의 의지를 조작하는 만능 기술로 단정하지 않는다. 세계의 비밀, 신호의 제작 이유, 결말의 진상은 별도 스토리 설계 단계에서 확정한다.

### 2.4 지역·세력 제안

| 지역/거점 | 기능 | 대표 자원·사건 |
|---|---|---|
| 방파제 거점 | 허브, 정비·상점·제작·NPC 대화 | 충전, 공구, 정비 기록, 생활 이벤트 |
| 침수 물류구역 | 위험도 낮~중 탐사 | 배터리, 기판, 구조 신호, 잠긴 창고 |
| 고철 해안 | 기계 잔해·희귀 부품, 스크랩 회수 | 관절 부품, 코어 외피, 폐기 기체, 구조 갈등 |
| 해저 중계시설 | 메인 미스터리·후반 위험 지역 | 신호 데이터, 특수 장비, 결말 조건 |

MVP에서는 방파제 거점과 침수 물류구역까지만 구현한다. 지역·세력 설명에 필요한 일반 NPC를 최소 2명 두고, 거점 상인/정비사는 게임플레이 기능을 제공한다. 주인공이 유일한 영웅이나 정해진 선택을 할 운명이라는 서사는 피한다.

## 3. 핵심 게임 루프와 시간

1. **거점:** 이전 기억·일기 확인, 기체 상태 점검, 수리·충전, 장비/아이템 제작 및 장착, 탐사 장소와 목표 선택.
2. **출발:** 탐사 비용(에너지·시간), 준비물 및 장비 적합성 확인. 자원 부족 시 이유를 명시하고 출발 전 수정 가능.
3. **탐사:** 장소의 고정 조사 포인트 + 조건부/가중치 랜덤 이벤트 + 메인 이벤트를 섞어 제시.
4. **선택:** 플레이어가 행동 의도를 지정. 성격·가치관·활성 기억·현재 감정·장비에 따라 수용·주저·거부·대안이 결정됨.
5. **해결:** 주인공의 실제 행동 확정 → 상황/능력/아이템에 따른 행동의 성공·실패·부분 성공 결정 → 세계 상태 변경.
6. **기록:** 선택 의도, 실제 행동, 결과, 비용, 성격 변화, 기억 태그를 원자적으로 기록하고 자동 저장.
7. **귀환:** 기체 수리·충전·제작·새 소식 확인. 게임 내 하루가 종료되면 확정된 사건으로 일기를 생성하여 저장.
8. **다음 날:** 일부 감정·피로의 일시 효과 완화, 일일 사건 가중치 재계산, 신규 사건 해금.

**게임 내 시간:** 현실 시간과 무관. 로그인 보상·자정 대기 없음. 첫 버전은 `탐사 1회 = 하루의 주 활동`, 귀환 시 일기 생성. 시간을 소모하는 중간 선택은 `timeCost`로 처리하지만 MVP에서는 복잡한 실시간 시간표를 만들지 않는다. 메인 사건은 출현 보장/조건부 고정 발동으로 RNG에 막히지 않는다.

**패배/진행 불가:** 기체 상태가 한계에 달해도 가능한 한 거점으로 구조되거나 위험을 감수한 결과를 반영하는 **fail-forward**를 우선한다. 긴 진행을 무작위 즉사로 잃는 구조는 첫 버전에 도입하지 않는다. 엔딩은 명시적으로 선택/사건 결과에 의해 도달하며, 확정 전에 저장한다.

## 4. 캐릭터 생성과 상태 모델

### 4.1 입력과 판정의 경계

- 입력: 이름, 대명사·호칭(선택), 외형 설명(자유 텍스트), 선택적 이미지, 기체 제작 목적, 성격 키워드 3개, 핵심 가치관 1개, 과거 서사 1개, 현재 소망 1개.
- 초기에는 플레이어가 기체 모델을 자유롭게 문장으로 써도 판정에는 영향을 주지 않는다. 판정에 영향을 줄 선택은 사전 정의된 ID를 사용한다.
- '의료형=이타적', '경비형=공격적' 같은 성격 고정 금지. 제작 목적은 기술/초기 장비·고유 사건에만 영향을 준다.
- 기존 키워드 간 충돌 허용. `신중함`과 `충동적임`이 동시에 있어도 오류가 나지 않아야 한다. 모순 조합은 장면별 우선순위·가중치로 해소한다.

### 4.2 상태의 다섯 층

| 층 | 데이터 | 변화 방식 | 플레이어 노출 |
|---|---|---|---|
| 초기 프로필 | 입력한 기체 목적·초기 성격·과거·소망 | 변경하지 않음 | 프로필에서 확인 |
| 성향 `traits` | 용기·이타성·신중함·충동성·사교성·경계심, 각 0~100 | 경험 결과를 통해 천천히 변경 | 정확한 숫자는 기본 비공개, 서술형 키워드로 표시 |
| 가치관 `values` | 핵심 가치관 ID와 강도 | 중요한 사건에서만 변화 | 가치관 텍스트 및 변화 힌트 |
| 감정 `emotions` | 공포·안도·죄책감·분노 등 0~100 | 사건/시간 경과에 따라 변동 | 표정·상태·일기 문장으로 간접 표시 |
| 경험·믿음 | 객관적 사건 참조 / 특정 믿음 ID와 강도 | 명시적 태그·조건으로 축적/완화 | 기억 전체와 일부 현재 인식 서술 |

**별도 물리 상태:** 배터리/에너지, 기체 손상도, 안정도(후유증), 인벤토리, 장비, 부품. `성격이 나빠졌다`처럼 단일 도덕적 수치는 만들지 않는다. 행동 강제 아이템의 대가는 **자기일치감/안정도 저하 및 관련 기억**으로 표현할 수 있으나, 캐릭터가 제4의 벽을 넘어 플레이어를 불신한다는 식으로 쓰지 않는다.

### 4.3 초기화 예시 — 개발용 값

- 여섯 성향 기본값 50. 키워드별 고정 보정치를 더한 뒤 0~100 범위로 제한. 같은 축을 여러 키워드가 강화하면 보정 상한을 둔다.
- 예시: `소심함`: 용기 -20, 경계심 +15 / `다정함`: 이타성 +20 / `신중함`: 신중함 +20, 충동성 -10.
- 기본값과 모든 키워드 보정치는 `character-options.json` 한곳에서 관리. 캐릭터 생성 화면의 설명과 실제 계산이 항상 일치해야 한다.
- 성향 표현은 임계값 하나에서 키워드가 계속 깜빡거리지 않도록 **히스테리시스**를 적용한다. 예: 새 키워드 획득 시 70 이상 2개 사건 동안 유지, 제거는 60 미만 2개 사건 동안 유지 등. 실제 수치는 테스트로 조정.

### 4.4 기술과 성향의 구분

기술은 `repair`, `scavenge`, `navigation`, `communication` 등 0~5 등급을 MVP에 맞게 소수만 사용한다. **기술 = 할 수 있는가**, **성향·가치관 = 하려고 하는가**, **실제 상황·도구 = 성공할 수 있는가**를 분리한다. 겁 많은 정비공도 정비 기술은 높을 수 있으며, 용감한 기체도 해당 기계를 고칠 지식이 없을 수 있다.

## 5. 행동 판정 엔진 — 필수 계약

### 5.1 데이터 흐름

`선택지 제공 → 행동 의도(choiceId) 확정 → 물리/상황 가능성 검사 → 캐릭터 성향 충돌 계산 → 수용/주저/거부·대안 확정 → (필요 시) 아이템 개입 → 실제 행동(actualActionId) 확정 → 행동 결과(outcomeId) 확정 → 상태 변경 → 기록/저장 → 다음 장면`.

**절대 섞지 말 것:** 선택 수용은 성공 여부가 아니다. 직접 구조를 *시도*할 수 있어도 실패할 수 있다. 행동을 거부했다고 곧바로 게임 오버가 되어서는 안 된다.

### 5.2 3종 판정

1. **물리·상황 게이트:** 장비 부족, 잠긴 문, 사용 불가 지역 같은 객관적 조건. 아이템으로 해결 가능한 조건과 불가능한 조건을 구분. 강제 명령은 물리적으로 불가능한 행동을 가능하게 만들지 않는다.
2. **의지/수용 판정:** 성향·가치관·관련 믿음/기억·감정으로 행동 충돌 점수 계산. 이벤트가 허용하는 경우에만 캐릭터의 거부/대안 분기 실행.
3. **행동 결과 판정:** 실제 행동과 기술·상황·아이템을 사용하여 성공/부분 성공/실패 결정. 사건별로 결과의 세계 상태 변경을 명시한다.

### 5.3 충돌 점수 v1 — 밸런스 가설

- 성격 항 최대 50점. 이벤트 선택지에 선언된 각 규칙 `weight × normalizedConflict`를 합산하고 50으로 제한. 높은 성향이 충돌하는 규칙은 `trait/100`, 낮은 성향이 충돌하는 규칙은 `(100-trait)/100` 사용. 무관한 성향은 계산하지 않는다.
- 가치관 항 최대 30점. `valueId`, 행동 태그, 가치 강도 및 충돌 심각도에 따른 규칙표로 계산.
- 경험·감정 항 최대 20점. 이벤트·행동에 적용되는 **활성 경험 효과만** 합산; 무관한 과거 사건 전체를 순회하지 않는다.
- 최종 `clamp(traitPart + valuePart + memoryEmotionPart, 0, 100)`.
- 충돌 0~39: 수용, 40~69: 거부 확률 5~15%, 70~100: 15~30%. 이는 **초기 테스트 범위**이며 로그를 보고 조정한다. 사건의 `autonomy.enabled=false`면 자율성 난수를 굴리지 않는다.
- `hardRefusal`은 매우 희귀한 명시적 사건 규칙으로만 사용. 최소한 하나의 진행 가능한 대체 선택/후속 사건을 반드시 제공한다.
- 갈등은 확률적 거부가 발생하지 않아도 망설임 문장으로 표현할 수 있다. 단, 문장만 보고 거부 여부가 뒤늦게 바뀌어선 안 된다.

### 5.4 정합성 우선 규칙

- `onRefuse`나 `onAlternative`로 이어지는 **작성된 유효 분기**가 없으면 RNG 거부 금지; 수용 또는 사전 작성한 망설임만 출력.
- 이벤트마다 `allowedActions`와 결과 분기를 선언. 엔진은 임의의 문장을 만들거나, 작성되지 않은 결과로 이동하지 않는다.
- 거부 후 선택지는 **새 단계**이며 원래 판정을 무한 재시도할 수 없어야 한다. 상황 변화·새 아이템·새 접근법이 있는 경우에만 다시 시도 가능.
- 신념 충돌과 난수 결과가 캐릭터의 제작 목적/기술을 완전히 무력화하지 않도록 중요 이벤트는 수동 검수.
- RNG는 **선택 확정 시 한 번만** 굴리고 결과·시드 상태를 저장. 새로고침·화면 전환·기억 재열람 시 재추첨 금지.

### 5.5 거부 연출의 세 단계

- `hesitate`: 선택 수행, 단 행동 묘사에 주저를 반영.
- `alternative`: 본래 목표는 지지하나 다른 행동을 제안하거나 수행. 예: 위험한 터널에 직접 진입 대신 드론 탐사.
- `refuse`: 선택 행동을 수행하지 않음. 새 선택지 열기 또는 사건의 정해진 후속 결과로 진행.

모든 단계에서 캐릭터는 플레이어의 존재를 언급하지 않는다. `내가 왜 그 명령을 거부했지?`는 세계 안에 **실제로 강제 명령 장치**가 사용되었을 때에만 허용. 일반 선택 거부는 `들어갈 수 없었다`처럼 행동 자체를 중심으로 서술.

## 6. 아이템·기체 상태·제작 시스템

### 6.1 아이템 분류

- **재료:** 고철, 구리선, 기판, 밀폐 패킹, 에너지 셀 등. 수량 제한/드롭 출처 기록.
- **소모품:** 충전팩, 임시 방수제, 응급 수리 키트, 강제 명령 모듈.
- **장비:** 절연 장갑, 수중 탐사용 센서, 휴대 드론. 장비 슬롯/내구도/에너지 소비.
- **단서·퀘스트 물품:** 문서, 코드키, 실종 기체 로그. 버리거나 분해해 메인 진행이 막히지 않도록 보호.

### 6.2 대표 아이템 명세 — 최초 구현안

| 아이템 | 획득/조건 | 효과 | 비용/부작용 | 제약 |
|---|---|---|---|---|
| 강제 명령 모듈 | 희귀 소모품 | **성격 충돌로 인한 거부 직후**, 기존 `intendedActionId` 실행을 1회 강제 | 안정도 -12(가설), 관련 부정적 기억 태그, 사용 흔적 기록 | 물리 불가능/이벤트가 금지한 행동/NPC 의지/성공 판정에는 적용 불가 |
| 기억 억제 칩 | 지정 장비 | 특정 활성 기억의 판정 효과를 탐사 1회 차단 | 그 기억이 제공한 유익한 주의 보정도 함께 차단; 사용 기록 | 기억 자체 삭제 금지; 과거 일기 수정 금지 |
| 소형 탐사 드론 | 장비 | `drone_access`가 선언된 선택지 추가, 위험 장소 선행 조사 | 드론 배터리/손상 | 모든 봉쇄구역을 통과하지 못함 |
| 임시 방수제 | 소모품 | 지정 횟수/장면 동안 침수 손상 감소 | 소재 소모, 효과 만료 | 심해 진입 가능 보장 아님 |
| 응급 수리 키트 | 소모품 | 안전한 상황에서 기체 손상 감소 | 부품 사용/행동 시간 | 코어 파손·완전 정지 기체를 만능 복구하지 않음 |
| 신호 스캐너 | 장비 | 비밀 신호 관련 조사 선택지/사건 가중치 해금 | 에너지 소비 | 스캐너 자체가 정답을 출력하지 않음 |

**강제 명령의 화면 흐름:** (A) 플레이어가 행동 선택 → (B) 성격 충돌로 거부 확정 및 이유를 암시하는 장면 → (C) `그대로 받아들이기/다른 방법 찾기/강제 명령 사용` 제시(아이템 보유·사건 허용 시) → (D) 사용 확인 및 예상 물리 비용 표시 → (E) 캐릭터가 **행동을 시도**, 별도 성공 판정 → (F) `forcedOverrideUsed=true`, 물리/정서 비용, 기억, 일기 후보를 모두 저장. 거부하기 *전* 사용 가능한 아이템은 다른 규칙/아이템으로 분리한다.

**부작용 설계:** 일률적인 도덕적 벌점이 아니라 원래 가치관과 실제 수행 행동의 거리, 부상·배터리 손실, 반복 사용 등에 따라 `안정도`, 특정 믿음, 표정/일기 서술을 다르게 한다. `강제 사용 횟수`만 보고 캐릭터가 자동으로 악인화되는 설계는 금지. 반복 사용에 따른 장기효과는 별도 스토리에서 검증한 후 추가.

### 6.3 제작과 경제

MVP 제작법 3~4개: 수리 키트, 방수제, 소형 드론 수리, 충전팩. 레시피는 재료 수량과 제작 가능 장소/기술/해금 플래그를 가진 정적 데이터. 제작 버튼 누르기 전 재료·획득 아이템·비용 미리 보기; 확정 시 원자적 수량 차감. 기본 탐사에서 필수 제작 재료를 무기한 놓치지 않도록 보장. 스크랩 노가다를 막기 위한 일별 드롭 상한/이벤트 피로도를 둔다.

### 6.4 생존 스탯

MVP 권장: `energy(0~100)`, `integrity(0~100; 100=완전한 상태)`, `stability(0~100)` 3개. `coreHealth`는 메인 사건 전용 플래그 또는 희귀 장기 상태로 시작하고, 배터리와 코어를 같은 자원으로 취급하지 않는다. 화면에 잔여 에너지/기체 손상은 명확히 보여주고, 성격·기억 수치는 기본 숨김. 회복 방법과 자원 고갈 시 보호 장치를 각 스탯별로 명세한다.

## 7. 탐사·사건·스토리 콘텐츠 시스템

### 7.1 사건 종류

- `main`: 장별 진행 플래그에 따라 확정 발동, 필수 단서는 반드시 얻을 수 있는 대체 경로 제공.
- `side`: 선행 사건·아이템·인물 관계·기억 조건으로 열림. 종결 상태 저장.
- `ambient`: 반복 가능한 짧은 탐사 사건. 동일한 문장 과다 반복 방지, 보상 상한, 일기 우선순위 낮음.
- `character`: 성격/믿음/출신·과거와 특정 지역의 조합에 의해 출현하는 캐릭터별 사건.
- `reaction`: 과거 선택 결과에 대한 후속 반응. 이전 기억 ID/결과 플래그와 연결된 사건만 호출.

### 7.2 3층 스크립트

**층 1 — 공통 사실:** 장소·관찰·발견 등 누구에게나 동일한 내용.  
**층 2 — 조건부 반응:** `경계심 높은 캐릭터`, `같은 장소에서 부상 경험`, `동행 NPC와 친밀` 등 명시된 조건에 따라 1개 이상의 문장 삽입.  
**층 3 — 실질 분기:** 플레이어 선택, 실제 행동, 기술/아이템, 결과에 따라 상태와 다음 장면이 변화. 모든 조건부 문장이 반드시 독립적인 서사 분기일 필요는 없지만, 중요한 선택에는 적어도 하나의 실제 상태 차이를 남긴다.

**문장 선택 우선순위:** 사건 전용 기억 반응 > 고유 가치관 반응 > 일반 성향 반응 > 기본 문장. 서로 배타적인 슬롯에서는 1개만 출력. 독립적인 묘사는 여러 개 붙일 수 있으나 문장 간 모순을 검사한다. `if`를 임의 문자열로 평가하지 않고 제한된 조건 연산자와 사전 정의된 태그만 사용한다.

### 7.3 자유도를 높이는 재사용 가능한 '행동 도구'

모든 사건에서 모든 아이템을 사용하는 것은 불가능하다. 대신 이벤트에서 `accessTags`를 선언하고 관련 기술·장비가 있으면 일반적인 추가 선택지를 생성하는 **태그 기반 상호작용**을 사용한다. 예: `locked`, `electronic`, `narrow`, `flooded`, `unstable`, `social`. `electronic`+정비 기술 → 전자 잠금 해제; `narrow`+소형 드론 → 원격 조사. 각각의 생성 선택지에도 실제 결과 분기가 작성되어 있어야 한다. 태그만 있으면 무조건 모든 문제 해결 가능하게 만드는 구현은 금지.

### 7.4 사건 선택과 반복 방지

- 현재 장소·날짜·스토리 단계·선행 플래그·획득 아이템에 따라 후보 집합 생성.
- 메인 이벤트는 별도 큐에서 우선 처리하며 난수에 막히지 않음. 일반 이벤트는 가중치 추첨.
- 직전 n개 사건, 같은 `eventFamily`, 동일 보상 반복에 감쇠/쿨다운 적용.
- 한 회차에 한 번만 발생하는 사건에는 `oncePerRun` 표시. 구조한 NPC가 동일 조건으로 또 처음 구조되는 사건 금지.
- 필수 단서·필수 재료의 모든 획득 경로를 상실하면 회복용 대체 이벤트를 보장.
- 로그/일기에서 같은 사건이 플레이어의 선택 없이 두 번 기록되지 않도록 `eventInstanceId` 사용.

### 7.5 스토리 구조 제안

`프롤로그: 거점 합류 → 1장: 침수 물류구역의 미확인 구조 신호 → 2장: 신호 송신원의 흔적과 공동체의 대립 → 3장: 해저 중계시설 접근 → 결말: 신호를 유지/격리/파괴 등`의 **대강의 골격**만 먼저 확정한다. 신호 진상, 원인, 인물 설정은 별도 스토리 바이블에서 개발한다. 서브 스토리는 최소한 메인 중간에 끼어들되 1회차의 정해진 인물 관계를 강요하지 않는다.

## 8. 기억·믿음·일기 설계

### 8.1 사건 기록은 단일 진실 공급원

모든 사건 해결은 `EventResolution` 한 건을 생산한다. 최소 필드: `eventInstanceId`, `eventId`, `gameDay`, `locationId`, `playerChoiceId`, `actualActionId`, `outcomeId`, `outcomeTags`, `itemUses`, `worldDelta`, `characterDelta`, `memoryIds`, `resolvedAtGameTime`. 이는 플레이어가 *하려 했던 것*, 주인공이 *실제로 한 것*, 실제로 *벌어진 것*을 엄격히 구분한다. 화면에 보여주기 위한 감상 문장은 사건 사실의 원본이 아니다.

### 8.2 기억창

- 시간순 타임라인. 하루·장소·인물·태그별 필터, 중요한 기억 즐겨찾기, 관련 사건 링크.
- 기억 카드: 날짜/장소/사건 제목/플레이어 선택/실제 행동/결과/관련 아이템/후속 영향 힌트.
- 객관 기록은 변조 금지. 주인공이 일기에 자기합리화를 해도 기억의 실제 결과는 바뀌지 않는다.
- 캐릭터의 내부 판정에서는 전체 로그를 매번 순회하지 않고, 저장된 `activeBeliefs` 및 관련 경험 태그 집계값을 사용.
- 플레이어의 저장 파일은 민감할 수 있으므로 기본적으로 기기 로컬에만 저장하고 외부 전송하지 않는다.

### 8.3 믿음 형성

사건마다 `experienceEffects`를 선언하여 `trust_strangers`, `fear_flooded_places`, `protect_others` 등 정의된 믿음의 근거 태그를 추가/완화. 서로 다른 사건 가족에서 일정 횟수 축적하면 새로운 믿음 활성화. 동일한 반복 이벤트 파밍으로 믿음이 급변하지 않도록 가족별 집계 제한. 믿음은 확실하게 사건과 연결되고, 회복·반증 경험으로 완화될 수 있다. MVP는 믿음 4~6개만 구현하고 자동 자유 생성 금지.

### 8.4 일기 생성 계약

`DaySummary(실제 사건 목록) + DiaryVoice(표현 성향) + Emotion(당일 반응) + RelevantMemory(관련 회고) → DiaryEntry(저장된 완성 텍스트)`.

- **사실 문장:** 각 `outcomeId`에 매핑된 사실 템플릿만 사용. 성공/실패/포기/강제 명령을 구분.
- **반응 문장:** 감정·가치관·성향·믿음 조건에 맞는 문장. 표현 스타일은 담백함/수다스러움/분석적임 등의 별도 축으로 취급. `무뚝뚝함=감정 없음`으로 처리하지 않는다.
- **회고 문장:** 과거 사건의 ID가 있을 때만 삽입. `아직 만나지 않은 NPC`나 `획득하지 않은 물건`을 언급하지 못하게 한다.
- **하루 요약:** 중요한 사건 1~2건 우선, 작은 사건 여러 개는 압축. 사건이 없으면 `정비하고 쉬었다` 등 **실제 발생한** 기본 활동으로 간단히 마무리.
- **강제 개입:** `forcedOverrideUsed`면 구별 가능한 전용 회고 후보를 추가하되, 모든 캐릭터가 동일한 후회를 표현하지 않도록 조건별로 다르게 한다.
- **저장:** 하루 종료 시 한 번 생성·저장(`day`, `text`, `sourceEventInstanceIds`, `templateIds`, `voiceId`). 과거 일기는 재생성하지 않는다. 사용자 편집 기능은 이후 별도 저장층에서만 제공.
- **테스트:** 문장 중복, 인칭/조사, 시간 순서, 하루 사건의 사실성, 템플릿 누락, 부정문 충돌(예: `무서웠지만 두렵지 않았다`) 검사. 가장 중요한 사실 문장은 문체 랜덤보다 우선한다.

### 8.5 비밀 수치 공개 정책

정확한 성향·거부 확률·믿음 강도는 기본 비공개. 프로필에는 `조심스러움`, `낯선 사람을 경계하는 듯하다` 같은 서술형 상태, 일기에는 자기인식의 변화 힌트를 노출. 에너지·손상·장비·제작 재료는 플레이 가능한 정보를 충분히 노출한다. 디버그 모드에서만 내부 수치·충돌 점수·RNG 시드·적용 템플릿을 볼 수 있게 한다.

## 9. UI/UX 설계 — 세로형 모바일 우선

### 9.1 정보구조

1. 시작/이어하기/새 캐릭터/저장 파일 가져오기.
2. 캐릭터 생성(기본 정보 → 제작 목적 → 성격 3개 → 가치관 → 과거/소망 → 검토).
3. **탐사**(상단 하루·에너지·손상, 장소 이미지/장면 텍스트, 선택지, 보유 장비에 따른 추가 선택, 사건 결과 확인).
4. **거점**(충전/수리/제작/장비 관리, 다음 목적지).
5. **캐릭터**(현재 성향 서술, 초기 설정, 상태, 기체 이미지).
6. **기억**(시간순 기록, 필터, 중요 기억 즐겨찾기).
7. **일기**(날짜별 회고, 해당 날짜 기억으로 이동).
8. **인벤토리/설정**(아이템 설명과 사용 조건, 백업/복원/접근성 옵션).

초기 하단 내비게이션은 `탐사 · 거점 · 캐릭터 · 기록` 4개로 제한하고 `기록` 내부에 `기억/일기` 탭을 둔다. 인벤토리는 탐사·거점에서 모두 열 수 있게 한다. 모든 조작은 터치만으로 가능해야 하며, 320 CSS px 너비에서도 선택지와 텍스트가 잘리지 않아야 한다.

### 9.2 장면 UI 상태 머신

`SCENE_READING → CHOICE_AVAILABLE → CHOICE_RESOLVING → [HESITATION/OVERRIDE_OFFER] → OUTCOME_READING → NEXT_SCENE`.

- 선택지를 누르는 즉시 버튼을 중복 클릭 불가능하게 만들고 결과를 확정/저장한다.
- 거부 시 `행동 강제`를 바로 자동 실행하지 않는다. 아이템 소지·사용 가능 조건·비용을 제시하고 사용자의 명시적 확인을 받는다.
- 결과 확인 화면에는 `플레이어 선택 → 실제 행동 → 결과`를 구분해 보여주되, 서사의 몰입을 해치지 않도록 짧은 요약은 접기 가능.
- 자동 스크롤은 새로운 장면 텍스트에 한정; 기록을 읽는 중 강제로 스크롤하지 않는다. 타이핑 애니메이션은 끄거나 즉시 전체 표시 가능.
- 글자 크기/행간 옵션, 충분한 대비, 탭 타깃 약 44px, 화면 읽기용 상태 변경 문구, 버튼 비활성 이유 표시.

### 9.3 시각·음향 방향

염분에 삭은 금속, 폐허의 흰 햇빛, 청색 바다, 경고등의 주황빛, 조용한 터미널 UI. **니어 오토마타의 자산이나 화면을 복제하지 않는다.** 이미지 없이도 전 장면 텍스트와 기호/간단한 배경으로 플레이 가능하게 먼저 구현. 이미지/음향은 후속. 사용자 업로드 이미지는 브라우저 내 처리·용량 제한·개인정보 안내.

## 10. 기술 아키텍처

### 10.1 권장 스택

- TypeScript + Vite 기반 정적 SPA. 기능 단위 모듈, UI 라이브러리 선택은 작은 프로토타입 이후 결정; 처음에는 지나치게 큰 프레임워크·상태관리 라이브러리를 강제하지 않는다.
- 콘텐츠 JSON + 버전 관리되는 타입 정의 및 검증 스키마. 외부 생성형 AI 호출, 사용자별 백엔드, 계정 시스템 없음.
- 저장: IndexedDB(`saves`, `assets`, `settings`)와 내보내기/가져오기 JSON. 작은 설정은 별도 안전 저장 가능. 브라우저 저장 공간은 삭제될 수 있으므로 백업 안내가 필요하다.
- 배포: GitHub Pages 등 정적 호스팅. 상대 경로/base path를 배포 위치에 맞게 설정; 새 버전에서도 기존 저장 데이터가 유지되도록 마이그레이션.
- 테스트: 순수 엔진 단위 테스트 + 데이터 검증 + 브라우저 E2E + 실제 모바일 테스트.

### 10.2 모듈 경계

| 모듈 | 책임 | 하면 안 되는 일 |
|---|---|---|
| `character` | 생성·현재 성향·가치관·기술·감정 | UI 직접 변경 |
| `content` | 위치·이벤트·아이템·대사·일기 템플릿 정적 데이터 | 코드 실행·임의 JS 주입 |
| `eventSelector` | 현재 상태에서 유효한 사건 후보/우선순위 | 선택 결과 확정 |
| `decisionEngine` | 상황 게이트·충돌 점수·수용/거부 판정 | 장면 텍스트를 사실 기록으로 사용 |
| `outcomeEngine` | 행동 성공/실패와 분기 결과 | 같은 선택을 두 번 평가 |
| `effectEngine` | 비용·보상·성격·믿음·세계 플래그 변경 | 저장·로그와 따로따로 커밋 |
| `journal` | 기억/일기 생성 및 조회 | 결과가 확정되지 않은 사건 기록 |
| `inventory` | 재료·장비·제작·사용 조건 | 무조건 아이템 사용 성공 처리 |
| `persistence` | 저장/복원/스키마 변경·백업 | 예전 저장 파일을 조용히 파괴 |
| `ui` | 화면 렌더링·접근성·입력 이벤트 | 임의로 성향/진행 플래그 수정 |

### 10.3 디렉터리 제안

```text
src/
  app/             # 부트스트랩, 라우팅, UI 상태
  core/            # eventSelector, decision, outcome, effects, RNG
  domain/          # character, inventory, memory, storyFlag 타입
  content/         # locations, characters, items, recipes, events, diary
  ui/              # creator, exploration, hub, inventory, memory, diary
  storage/         # IndexedDB, backup, migrations
  validation/      # 콘텐츠/세이브 스키마 검증
  assets/          # 자체 제작 이미지·효과음
  tests/           # 단위·통합 테스트
public/
docs/               # 이 문서, 세계관 바이블, 콘텐츠 작성 가이드
```

**모든 데이터 변경은 하나의 `resolveAndCommitAction()` 경로로 처리한다.** UI·일기·기억창이 직접 캐릭터 수치나 플래그를 고치지 않게 한다. 렌더링은 확정된 결과를 소비하는 역할이다.

## 11. 데이터 타입 및 콘텐츠 계약

다음은 전체 스키마의 핵심을 보여주는 **TypeScript 인터페이스 초안**이다. 구현 시 Zod·JSON Schema 등으로 런타임 검증을 추가하고, 실제 필드 구조를 하나의 코드 파일에서 관리한다.

```ts
type TraitId = 'courage'|'altruism'|'caution'|'impulsivity'|'sociability'|'wariness';
type EventId = string;
type ActionId = string;
type OutcomeId = string;
type ItemId = string;
type MemoryTag = string;

type TraitMap = Record<TraitId, number>; // all integers, 0..100

type Condition =
  | { type:'flag'; id:string; exists:boolean }
  | { type:'item'; id:ItemId; minCount:number }
  | { type:'trait'; id:TraitId; op:'gte'|'lte'; value:number }
  | { type:'belief'; id:string; op:'gte'|'lte'; value:number }
  | { type:'storyStage'; id:string }
  | { type:'memoryTag'; id:MemoryTag; minCount:number };

type ConflictRule = {
  trait: TraitId;
  direction: 'high'|'low';
  weight: number; // nonnegative; trait subtotal clamped to 50
};

type Choice = {
  id: string;
  textId: string;
  conditions: Condition[];
  intendedActionId: ActionId;
  conflicts: ConflictRule[];
  valueConflictIds: string[];
  experienceConflictIds: string[];
  autonomy: {
    enabled: boolean;
    onAccept: string; // valid authored node ID
    onRefuse?: string; // REQUIRED if refusal possible
    onAlternative?: string;
    hardRefusal?: boolean;
  };
};

type Outcome = {
  id: OutcomeId;
  actualActionId: ActionId;
  result: 'success'|'partial'|'failure'|'abandoned';
  textIds: string[];
  tags: string[];
  effects: GameEffect[]; // structured, whitelisted effect union
  nextNodeId?: string;
};

type EventResolution = {
  eventInstanceId: string;
  eventId: EventId;
  gameDay: number;
  locationId: string;
  playerChoiceId: string;
  intendedActionId: ActionId;
  actualActionId: ActionId;
  outcomeId: OutcomeId;
  result: Outcome['result'];
  forcedOverrideUsed: boolean;
  itemUses: { itemId: ItemId; count: number }[];
  outcomeTags: string[];
  appliedEffectIds: string[];
  memoryIds: string[];
};

type SaveData = {
  saveVersion: number;
  runId: string;
  rngState: string;
  gameDay: number;
  activeScene?: { eventInstanceId:string; nodeId:string; phase:string };
  character: CharacterState;
  world: WorldState;
  eventLog: EventResolution[];
  memories: MemoryEntry[];
  diaries: DiaryEntry[];
};
```

**조건식은 선언형 데이터만 허용한다.** 콘텐츠 JSON 내부의 JavaScript 문자열 실행, `eval`, 자유로운 표현식 파서, HTML 삽입 금지. 이벤트 텍스트는 텍스트 노드로 렌더링하여 이름·자유 입력이 HTML/스크립트로 해석되지 않게 한다.

### 11.1 이벤트 JSON 샘플 — 일관성 중심

```json
{
  "id": "flooded_warehouse_signal_01",
  "locationId": "flooded_warehouse",
  "category": "side",
  "oncePerRun": true,
  "conditions": [{"type":"flag","id":"warehouse_open","exists":true}],
  "startNodeId": "signal_start",
  "nodes": [
    {
      "id":"signal_start",
      "textIds":["warehouse_signal_intro"],
      "choices":[
        {
          "id":"enter_directly",
          "textId":"choice_enter_directly",
          "conditions":[],
          "intendedActionId":"enter_dangerous_corridor",
          "conflicts":[{"trait":"courage","direction":"low","weight":35}],
          "valueConflictIds":[],
          "experienceConflictIds":["fear_flooded_places"],
          "autonomy":{
            "enabled":true,
            "onAccept":"entered_corridor",
            "onRefuse":"hesitated_at_corridor",
            "onAlternative":"consider_remote_scan"
          }
        },
        {
          "id":"scan_with_drone",
          "textId":"choice_scan_with_drone",
          "conditions":[{"type":"item","id":"scout_drone","minCount":1}],
          "intendedActionId":"deploy_drone",
          "conflicts":[],
          "valueConflictIds":[],
          "experienceConflictIds":[],
          "autonomy":{"enabled":false,"onAccept":"drone_scan_result"}
        }
      ]
    },
    {"id":"entered_corridor","textIds":["corridor_entered"],"outcomeTableId":"corridor_enter_roll"},
    {"id":"hesitated_at_corridor","textIds":["corridor_refused"],"overrideOfferId":"force_enter_once","nextNodeId":"post_refusal_choices"},
    {"id":"consider_remote_scan","textIds":["corridor_alternative"],"nextNodeId":"post_refusal_choices"},
    {"id":"drone_scan_result","textIds":["drone_scan_text"],"outcomeTableId":"drone_scan_outcome"}
  ]
}
```

샘플의 `outcomeTableId`, `overrideOfferId`, 결과별 텍스트·효과·다음 노드는 **다른 데이터 테이블에 실제 정의되어야** 한다. 위 예시는 실행 완료 JSON이 아니라 스키마·분기 설계 방향을 보여주는 축약본이다. 구현 시 `unknown reference`, 끝없는 루프, 도달 불가능 노드, 완료되지 않은 진행 경로를 빌드 단계에서 모두 검사한다.

### 11.2 저장 안정성

- `runId + eventInstanceId + resolutionPhase`로 중복 적용 방지. 사용자가 버튼을 두 번 누르거나 새로고침해도 아이템/보상/성향 변화가 중복되지 않는다.
- 결과 판정 → 검증 → 적용할 새 상태 및 로그 작성 → IndexedDB 한 트랜잭션으로 커밋 → UI 반영. 저장 실패 시 사용자에게 재시도/백업 경고, 잘못된 성공 안내 금지.
- 저장 포맷에 `saveVersion` 포함, 버전 업 시 순차 migration. 구버전 저장은 테스트 통과 후 지원. 미래 버전/손상된 파일은 원본을 덮어쓰지 않고 명확한 오류 표시.
- JSON 백업에는 버전·메타데이터·진행·일기·기억 포함, 이미지 포함 여부/용량 별도 명시. 파일 가져오기 전 미리보기·확인·용량 제한·스키마 검증. 기존 진행 덮어쓰기 전 별도 슬롯 저장 또는 확실한 확인 단계.
- 이미지 보관은 용량·브라우저 저장 한계를 고려해 썸네일로 축소 후 별도 `assets` 저장. 사용자 업로드를 외부 서버에 올리지 않는다.

## 12. 최소 플레이 가능 버전(MVP)의 정확한 범위

**목적:** 1회차가 시작부터 에필로그까지 실제 플레이되고, 같은 이벤트도 캐릭터 설정·아이템·기억에 따라 달라지는지를 검증한다. 개발 시간 예측이나 콘텐츠 100개 생산을 약속하는 단계가 아니다.

| 기능 | MVP 범위 | 나중으로 미루는 것 |
|---|---|---|
| 캐릭터 | 인간형 안드로이드 1기, 목적 3종, 성격 키워드 12~18개, 가치관 4개, 과거 4개, 소망 4개 | 인간/동물형/다중 주인공, 자유 입력 서사 이해 |
| 상태 | 6성향·3물리 상태·4감정·4~6믿음 | 복잡한 신체 부위별 손상, 수십 가지 심리 지표 |
| 지역 | 허브 1 + 탐사 1~2지역 | 오픈월드 지도·해저 전역 |
| 콘텐츠 | 독립 사건 약 10~15개 + 짧은 메인 에피소드/에필로그 2~3종 | 장편 멀티챕터·100개 이상의 사건 |
| 아이템 | 약 8종: 재료·회복·드론·강제 명령 | 광범위한 경제/거래/내구도 시뮬레이션 |
| 제작 | 3~4개 레시피 | 대규모 테크트리 |
| NPC | 기능 NPC 2명 + 구조/탐사 대상 | 복잡한 관계/연애/동료 AI |
| 기록 | 전 사건 선택·행동·결과 + 1일 1회 저장 일기 | 자유로운 무한 일기 생성 |
| UI | 모바일 4탭, 접근성 기본, 자동 저장·백업 | 커스텀 테마 에디터·모든 화면 애니메이션 |

**첫 실험용 대표 사건:** 침수 창고의 구조 신호. 위험한 통로에 직접 진입할지, 드론으로 살필지, 구조를 포기할지 선택. 겁 많은 캐릭터는 진입을 주저/거부할 수 있음. 강제 명령 사용은 직접 진입 **시도**를 보장하되 성공은 별도 판정. 성공·부분 성공·실패·포기마다 다른 기억과 일기 문장, 후속 사건 플래그 남김. 이 사건이 독립적으로 완주되지 않으면 콘텐츠를 대량 확장하지 않는다.

### 12.1 개발 순서와 각 단계 완료 조건

1. **P0 — 프로젝트 뼈대:** 실행/배포 가능한 모바일 페이지, 타입·스키마, 저장 슬롯, 기본 내비게이션. *완료:* 모바일에서 새 게임 생성·재접속·불러오기 가능.
2. **P1 — 캐릭터/판정 순수 엔진:** 캐릭터 생성, 고정 난수 시드, 물리 게이트, 충돌·수용·거부·대안, 실제 결과 분리. *완료:* 단위 테스트로 모든 분기 재현, 무효 분기 없음.
3. **P2 — 대표 사건과 아이템:** 사건 1개 완결, 강제 명령·드론·회복품 적용, 효과 원자적 커밋. *완료:* 수용/거부/강제/실패/부분 성공 시나리오를 실제 UI에서 재현.
4. **P3 — 기억/일기:** 객관 로그/활성 기억/믿음/하루 회고. *완료:* 사실 모순 없이 과거 일기 보존, 같은 사건 반복 적용 없음.
5. **P4 — 탐사/콘텐츠:** 허브·지역·사건 선택/반복 방지, 제작, NPC, 짧은 메인 에피소드/결말. *완료:* 시작부터 엔딩까지 다른 성향으로 2회 이상 플레이 가능.
6. **P5 — 출시 품질:** 실제 Android 브라우저·작은 화면·키보드 조작·데이터 백업·저장 복구·모바일 레이아웃·장시간 누적 플레이 검증. *완료:* 알려진 치명적 진행 중단/저장 손실 버그 없음; 남은 제약은 릴리스 노트 기록.

## 13. 테스트 계획과 품질 기준

### 13.1 엔진 단위 테스트

- 낮은 용기/높은 이타성/강한 가치관/관련 트라우마가 충돌 점수에 예상 방향으로 반영됨.
- 모든 수치는 범위 내, NaN·음수 아이템·중복 보상 없음.
- 같은 캐릭터+사건+시드+선택이면 같은 판정 결과.
- 거부 분기 없는 선택지에서 거부 발생 0회. 물리 불가능 행동은 강제 명령으로 실행 불가.
- 아이템 사용 시 수량 1회 감소·부작용 1회 적용. 행동 성공 보장은 적용되지 않음.
- 메인 사건은 유효 조건에서 RNG에 의해 무기한 미출현하지 않음.

### 13.2 콘텐츠 검증 자동화

- 모든 이벤트/노드/문장/아이템/믿음/레시피 ID 유일함.
- 모든 참조 ID 존재, 사용하지 않는 필드/알 수 없는 조건 연산자 오류 처리.
- 시작 노드 존재, 엔딩 또는 탈출 가능한 경로 존재, 고립 분기 없음.
- `autonomy.enabled`와 `onRefuse` 정합성, 아이템 오버라이드 허용 범위 검증.
- 메인 필수 단서 획득 가능한 경로, 소모·판매 금지 아이템 표시.
- 결과마다 로그용 `actualActionId`, `outcomeId`, 일기 사실 문장 및 세계 플래그 명세.
- 같은 날짜 1개 일기, 일기 원본 사건 참조 ID 존재, 미래 사건 참조 없음.

### 13.3 시나리오 플레이 테스트 — 필수 사례

| 사례 | 통과 기준 |
|---|---|
| 겁 많고 다정한 기체 vs 대담·경계심 높은 기체 | 같은 선택에서 충돌 점수·반응이 설계 의도에 맞게 달라짐. 난수 때문에 항상 다른 결과가 나올 필요는 없음 |
| 구조를 시도했지만 거부 → 드론 투입 | 객관 기억에 최초 의도·실제 원격 조사·최종 결과 구분 |
| 구조를 거부 → 강제 명령 → 시도 후 실패 | `시도`와 `실패` 모두 기록; 구조 성공 일기 출력 금지 |
| 구조 포기 후 해당 지역 재방문 | '처음 발견' 사건 중복 없음, 포기 결과에 맞는 후속 변화 |
| 장비 없이 장비 전용 선택 열기 | 선택 비노출 또는 비활성 이유 표시, 강제 실행/음수 인벤토리 없음 |
| 탐사 중 새로고침/오프라인 전환 | 확정된 분기·사용품·저장된 일기 보존, 난수 재추첨 없음 |
| 백업 후 복원 | 캐릭터·세계 플래그·기억·일기·소모품 상태 완전 일치 |
| 성격 임계값 근처 반복 플레이 | 프로필 표현이 매 사건마다 반대로 튀지 않음 |

### 13.4 모바일/접근성 수동 테스트

Android Chrome, 삼성 인터넷, 가능하면 다른 모바일 브라우저와 PC에서 확인. 320/360/390 CSS px 화면, 세로 방향, 큰 글꼴 설정, 확대, 터치 중복, 긴 캐릭터 이름, 입력 키보드 열림/닫힘, 스크롤 위치, 이미지 없는 모드, 데이터 저장 용량 초과, 오래된 저장 파일, `뒤로 가기` 동작을 점검. **개발 환경에서 테스트 통과한 것과 실제 기기에서 확인한 것은 별도 기록**한다.

## 14. AI/개발자 협업 규칙

### 14.1 역할 분담 제안

| 담당 | 산출물 | 변경 허용 범위 |
|---|---|---|
| 시스템 설계 담당 | 타입·판정식·상태 전이·공통 효과 규칙 | `core/`, `domain/`, 관련 테스트 |
| 콘텐츠 담당 | 세계관 바이블, 이벤트 그래프, 텍스트, 아이템·일기 템플릿 | `content/`와 콘텐츠 테스트; 공통 타입 독단 변경 금지 |
| UI 담당 | 모바일 캐릭터 생성/탐사/기록/아이템 화면 | `ui/`, 스타일 및 접근성 테스트; 판정 규칙 독단 변경 금지 |
| 저장·검증 담당 | IndexedDB, 내보내기/가져오기, 마이그레이션, 스키마 검사 | `storage/`, `validation/`, 테스트 |
| 통합 담당 | 의존성·공통 타입 합의, 병합, E2E, 브라우저 점검 | 공통 API 계약 및 릴리스 문서 |

한 번에 여러 AI가 같은 파일을 수정하지 않게 **작업 브랜치·모듈 경계를 먼저 지정**한다. 반드시 PR/커밋 단위로 작업하고, 변경 파일·이유·테스트 결과·남은 문제를 보고받는다. 데이터 포맷이나 ID 규약이 바뀌면 반드시 관련 모듈 담당에게 알리고 schema/version 및 마이그레이션을 동시 업데이트한다.

### 14.2 매 작업의 기본 인수인계 형식

```text
작업명:
기준 브랜치 / 기준 커밋:
작업 대상 파일:
변경하지 말아야 할 파일:
기존 계약(타입·ID·입출력):
구현 요구사항 / 비요구사항:
완료 조건(재현 가능한 테스트):
실행한 테스트와 결과:
남은 한계·주의사항:
```

### 14.3 타 AI에게 넘길 공통 프롬프트

> 너는 규칙 기반 모바일 SF 아포칼립스 텍스트 RPG의 개발 협업자다. 먼저 이 제작 계획서와 현재 저장소 구조를 읽고, **사용자가 직접 선택하는 게임**이라는 핵심을 유지하라. 플레이어의 선택 의도, 캐릭터의 실제 행동, 확정된 결과를 분리한다. AI API나 자유 생성 스토리는 도입하지 않는다. 캐릭터가 플레이어를 인지하는 메타 서사는 금지한다. 사건 콘텐츠가 직접 게임 상태를 변경하지 말고 공통 효과 엔진을 사용하라. 요청된 모듈 밖의 구조 변경은 하지 말고 필요하면 변경 제안만 작성하라. 구현 후 실제 실행한 테스트와 미실행 테스트를 구분해 보고하라. 이미 있는 기능·스타일·저장 데이터를 손상시키지 말고, 변경 전후의 브라우저 동작을 검증하라.

### 14.4 의사결정 로그

이 문서의 변경사항은 `docs/decisions.md`에 날짜/결정 내용/이유/영향 모듈/마이그레이션 필요 여부를 남긴다. 예: `2026-XX-XX: 주인공 유형을 인간형 안드로이드로 MVP 한정, 정식판 확장은 미정`. 아이디어를 합의된 사양처럼 다른 AI에게 전달하지 않는다.

## 15. 위험·우선순위·확장 로드맵

| 위험 | 징후 | 예방/대응 |
|---|---|---|
| 분기 폭발 | 신규 사건마다 기체·키워드 조합별 문장을 전부 새로 작성 | 공통 사실+조건 문장+중요한 실질 분기의 3층 구조, 템플릿 재사용 |
| 거부로 인한 플레이 피로 | 플레이어가 원하는 선택이 자주 실패하거나 거부 이유를 이해 못함 | 낮은 기본 거부 확률, 작성된 대안 제공, 거부 발생 로그·테스트 조정 |
| 수치 파밍 | 동일 행동 반복으로 성향·아이템 무한 획득 | 이벤트 가족별 한계, 실제 결과 기반 변화, 드롭 상한 |
| 일기 모순 | 구조 포기했는데 성공했다고 기록 | `outcomeId` 기반 사실 템플릿, 한 번 생성 후 저장, 자동 검증 |
| 저장 손상 | 브라우저 종료 후 진행이 이전 장면으로 돌아감 | 결과+효과+로그 원자적 커밋, 중복 방지, 백업/복구 테스트 |
| 콘텐츠 부족 | 탐사에서 동일 문장만 반복 | 이벤트 피로도, 고정 스토리 큐, 지역/장비별 후속 사건 개발 |
| 정적 호스팅 제약 | 로그인/기기간 자동 동기화 불가 | 로컬 저장 범위를 명시, JSON 백업 기능 우선. 계정/클라우드는 차후 별도 설계 |
| 미검증 '작동함' 주장 | 한 브라우저만 확인했는데 전체 모바일 호환이라고 공지 | 테스트 매트릭스 기록, 브라우저별 실제 확인 결과 공개 |

**릴리스 순서:** 폐허 구조 사건을 종단 간 구현 → 허브+짧은 완결 에피소드 → 공개판 콘텐츠 확대 → 관계/NPC 동료·복수 캐릭터·방대한 제작·새 지역 확장. 개발 우선순위는 `선택의 결과 정합성 > 저장 안정성 > 모바일 조작성 > 캐릭터 개성 > 아이템·탐사 다양성 > 시각 연출의 풍부함`.

## 16. 다음 작업 착수 지시 — 다른 AI에게 바로 넘기기

**첫 작업: 문서만 읽고 전체 게임을 단숨에 구현하지 말 것.** 현재 저장소가 없다면 TypeScript 정적 웹 프로젝트를 만들고, `CharacterState`, `Choice`, `EventResolution`, `SaveData` 타입과 1개의 테스트 이벤트를 작성한다. 그다음 선택 수용/거부/대안/강제 명령/행동 실패를 처리하는 **순수 엔진**과 재현 가능한 테스트를 구현한다. UI는 이 엔진의 확정 결과를 읽는 간단한 탐사 화면부터 연결한다. 저장 후 새로고침 테스트를 통과하면 기억창과 일기를 붙인다.

**제출물:** (1) 실행 가능한 소스와 실행/배포 방법, (2) 테스트 1개 사건의 모든 분기 표, (3) 플레이 로그 샘플 3종(수용 성공·거부 후 대안·강제 후 실패), (4) 실제 실행한 테스트 결과, (5) 알려진 미완성 기능과 다음 단계 권고. `코드 작성 완료`를 `정식 게임 출시 준비 완료`라고 보고하지 말 것.

**프로젝트의 최종 판단 기준:** 캐릭터가 내 선택을 거부했을 때 플레이어가 '버그'가 아니라 '이 캐릭터는 지금 그 행동을 하고 싶지 않구나'라고 이해할 수 있는가? 그리고 그 순간이 기억·일기·다음 사건에 실제로 남는가? 이 질문에 ‘예’라고 답할 수 있어야 이후 콘텐츠 확장을 진행한다.
